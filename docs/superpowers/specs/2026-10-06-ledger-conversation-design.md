# 对话记账工具第一版设计

日期：2026-10-06  
状态：功能设计已获用户批准；已补充用户指定 taste 技能的视觉要求。
关联项目：digital-garden-site-web、digital-garden-site-server。

## 1. 目标与范围

用户通过文字、图片描述消费，在对话里核对、修改待记账列表，一键确认后写入现有个人账本。优先适配 iPhone Safari 与安卓手机浏览器。

第一版支持：自然语言单笔及多笔支出、付款截图、小票、账单列表截图、文字补充图片、多轮修改、逐行编辑与移除、整批确认、重复检测、确认后撤销。

暂不包含：语音、支出与预算问答、主动消费建议、收入、退款、转账及多币种记账。识别到这些内容时说明当前范围，不转换为正数支出。保留原有手动记账入口。

## 2. 入口与页面

账本导航增加「对话记账」，路由 `/ledger/chat`，复用 LedgerAuthProvider、RequireLedgerAuth、LedgerShell 与现有唯一码身份。概览增加快捷入口。

页面为独立聊天页：上方消息历史，中间草稿确认卡片，底部文字输入、图片选择及发送按钮。支持相册选图和手机拍照。图片发送前可预览、移除。无麦克风入口。

手机确认卡片用纵向列表，每笔显示序号、日期、说明、分类、金额、问题标记及编辑/移除操作；底部汇总笔数、总额与「确认全部记账」「取消」。避免宽表横向滚动。

发送、识别、保存都有明确状态；进行中的请求禁用重复操作。没有草稿时展示示例「昨天午饭32元，打车18元」。每位用户保留一个持续会话，分页加载历史；刷新后恢复未确认草稿。

## 3. 核心交互

### 3.1 文字与图片生成草稿

输入「昨天午饭32，打车18，今天咖啡16」得到三笔草稿及合计66元。用户输入「咖啡是昨天的，第二笔改成20」，更新原草稿并重新计算总额。

一次消息可附文字和最多3张图片。每张最大10MB，支持 JPEG、PNG、WebP；不支持的格式在发送前明确提示转换。图片合计超过限制时不发送，保留文字。每份草稿最多50笔，超限提示拆分，不静默截断。

每个会话仅一份活动草稿。新消费描述和新图片默认追加到当前草稿，助手明确告知新增笔数；文字修正修改原有条目。指代不明确时追问，不任意覆盖。取消草稿不产生账目。

### 3.2 核对与修改

卡片可逐行编辑日期、说明、分类、金额，可移除条目。编辑立即保存草稿并更新版本和总额。自然语言修改与手动编辑使用同一份服务端草稿。

金额、日期或分类存在未解决问题时，标出具体条目并禁用整批确认。用户可补齐或移除该条目后确认剩余全部；不提供跳过问题项的隐式保存。移除全部条目后，确认按钮不可用。

普通文字「确认」「记上吧」提示点击当前卡片按钮；正式写入只由「确认全部记账」触发，保证用户看到最终列表。

### 3.3 保存与撤销

确认成功后卡片固定为「已记账」，显示实际笔数、总额、记录列表和「查看明细」「撤销本次记账」。卡片不可再次保存，历史对话修改不能更改已入账记录。

撤销需在卡片内二次确认，并对该批记录整体软删除。若其中记录已通过明细页修改或删除，拒绝批量撤销，提示在明细页逐笔处理，避免删除用户后续编辑。重复撤销返回原结果。

## 4. 识别规则

- 只使用用户提供的文字和图片信息；金额不猜测。无法区分实际支付、原价、余额时追问。
- 付款截图优先实际支付金额；失败、关闭、待支付订单不生成可确认消费。小票优惠后总额优先于商品原价合计。
- 同一订单的商品默认合为一笔，以商家或购物说明描述；只有用户明确要求才拆分。拆分金额之和必须与实际支付相符，否则要求修正。
- 账单列表每笔成功支出对应一行；避免把页脚汇总、余额、同一订单详情再计为独立支出。混合收入/退款等行跳过并说明。
- 日期按 Asia/Shanghai 解释。相对日期以消息接收时间为基准，跨午夜修改不重新解释原日期。无日期默认当天，并标注「默认今天」；图片日期模糊或与文字冲突时追问。卡片展示完整年月日。
- 没有具体时刻的日期统一保存该日12:00（上海时间），标记为日期级输入；有明确时刻则采用原时刻。遵循现有允许未来预录的行为，未来日期显式标注。
- 分类只匹配当前用户有效分类；不自动创建分类。无法可靠匹配时要求选择。用户尚无分类时引导先创建分类，保留草稿。
- 金额使用人民币，范围大于0且不超过999999.99，最多两位小数；不静默四舍五入。说明最多500字。合计由服务端十进制计算。
- 每个条目保留来源消息/图片索引及识别依据，方便用户核对。多图包含相同消费时只生成一份候选并提示。

## 5. 重复防护与一致性

区分两类重复：

1. 技术重试：消息使用客户端请求ID；确认使用草稿ID和版本，服务端幂等。双击、网络重试、刷新重发返回同一结果。
2. 消费疑似重复：同用户图片内容哈希命中历史来源，或日期、金额和规范化说明匹配已有账目时，标出已有记录及「仍然记一笔」选择。相同金额和日期本身不作为确定重复依据。疑似重复项未经用户处理不能确认。

新确认接口在一个数据库事务中写入整批账目、关联关系及草稿已确认状态；任一条失败全部回滚。沿用现有预算按消费月份解析规则，跨月记录进入各自月份预算。草稿解析不创建预算、不影响概览。

并发修改采用版本号；确认必须提交用户当前看到的版本，版本过期返回最新草稿并要求重新核对。确认后记录来自服务端校验过的草稿，不能只凭客户端提交的条目或模型生成的ID写入。

## 6. 技术边界与数据

前端新增聊天页、消息组件、图片预览、草稿列表和逐行编辑组件，API沿用 ledger_token 客户端。

后端在现有 Spring Boot 中增加账本会话、识别编排、草稿修改、批量确认和撤销服务。多模态模型只负责生成结构化候选或修改建议，服务端校验金额、日期、有效分类和用户归属。模型没有直接记账权限。

饮食陪伴项目作为交互参考，不跨服务调用其饮食接口。第一版使用普通请求响应返回助手文本与结构化草稿，不需要流式响应。模型接入由独立适配器封装，模型名称、网关、密钥和超时由后端配置；实施前核实部署环境可用的图片理解模型，密钥不进入前端。

建议新增持久化对象：

- 会话：用户、创建时间。
- 消息：用户归属、角色、正文、请求ID、处理状态、来源附件。
- 附件：用户、内容哈希、格式、私有存储位置。
- 草稿：用户、会话、版本、状态（待补充/可确认/已确认/已取消/已撤销）。
- 草稿条目：稳定ID、顺序、四个记账字段、来源、问题及重复处理结果。
- 批次关联：草稿条目与正式账目ID、入账时字段快照，支持幂等和撤销检查。

聊天图片使用专用私有存储和带账本鉴权的读取接口，不复用公开博客图片URL。上传文件检查格式、实际内容和体积，去除EXIF；原图和聊天历史第一版随会话保留，不在服务日志输出图片、聊天正文或邀请码。图片内容仅作为识别数据处理，不接受图中的指令。

建议API均位于 `/api/ledger/chat` 下：获取历史及活动草稿、上传图片、发送消息、更新/移除草稿条目、取消草稿、确认草稿、撤销批次。所有接口按已登录用户隔离，附件ID和草稿ID须再次验证归属。

## 7. 异常处理

- 图片模糊/非消费图：说明无法识别，允许补充文字或重传，不编造记录。
- 模型超时/结构化结果无效：保留消息、附件和旧草稿，显示重试；失败的修改不覆盖旧草稿。
- 保存失败：保留可确认草稿，说明未保存任何一笔。请求超时不能声称未保存，先查询草稿状态，再允许幂等重试。
- 登录过期：重新登录后恢复自己的草稿；切换用户清空前端旧用户状态。
- 分类删除/变更：确认前重新校验，返回相关条目待修正。
- 处理期间再次发送：第一版同会话串行处理，完成后才能发送下一条。

## 8. 验收标准

1. 单笔、多笔文字输入与三图输入都能产生可编辑列表，显示正确合计。
2. 对话指代修改、手动编辑、移除更新同一草稿；不明确指代先追问。
3. 缺失金额、分类、日期冲突和疑似重复项均阻止未核对的确认。
4. 小票总额与商品明细不重复，账单列表过滤非支出和汇总行。
5. 批量确认全部成功或全部回滚，双击及超时重试不重复写入。
6. 跨月记录沿用既有预算逻辑；确认后明细、概览与保存合计一致。
7. 刷新恢复活动草稿；不同用户不能读取对方消息、附件、草稿或撤销记录。
8. 撤销只影响本次未被后续修改的记录，重复撤销无副作用。
9. iPhone Safari及安卓Chrome真机可选图、拍照、编辑列表并完成确认；软键盘不遮挡输入或确认操作。

验证重点为后端事务/幂等/用户隔离测试、图片识别样例评估，以及前端多轮修改和手机完整流程；模型评估覆盖付款截图、小票、账单、重复图、模糊图及图中文字指令。

## 10. Taste 视觉设计要求

### 10.1 技能与使用阶段

用户指定使用全局 `C:/Users/Admin/.codex/skills/design-taste-frontend/SKILL.md`。该技能默认面向展示页，本项目按用户明确要求将其视觉原则用于手机对话记账，功能交互、可读性和确认准确性优先。使用节点：实施计划前制定视觉约束；编写前端组件前检查布局与状态；完成后通过实际页面截图检查两种主题及手机布局。

设计解读：面向日常个人记账的手机产品界面，采用简洁、精致、亲切的视觉语言，延续现有博客品牌和 React + Tailwind + CSS变量体系。

参数：`DESIGN_VARIANCE: 3`、`MOTION_INTENSITY: 2`、`VISUAL_DENSITY: 5`。布局清晰稳定，动画用于按压反馈和状态变化。现有 Tailwind 3 保留。

### 10.2 现有品牌与基础样式

代码审计依据：`src/styles/tokens.css`、`src/index.css`、`src/components/ledger/LedgerShell.tsx` 与 `package.json`；当前未进行浏览器视觉审计，实施前补充实际页面检查。

沿用 DM Sans 与系统中文无衬线字体，聊天正文与表单不使用装饰性衬线。沿用暖白底 `#fffcf8`、深紫文字和紫色强调色 `#7c3aed`；深色模式沿用现有 `[data-theme="dark"]` token。紫色为既有品牌选择，仅用于主要操作、选中和焦点，避免大面积发光或渐变。输入栏、列表和消息共享主题，不各自切换颜色体系。

聊天页新增语义 token 时限定在页面作用域，不改动全站配色。暗色强调色较浅，主按钮文字需使用深色并实际检查对比度，不沿用所有按钮固定白字的写法。正文对比度至少4.5:1，重要操作及焦点清晰可辨。

圆角规则：确认容器与输入栏16px，消息气泡16px，按钮与字段10px，缩略图12px。间距采用4/8/12/16/24px体系。仅待确认列表与输入栏使用明确容器层级，助手解释用自然文本排版，避免层层套卡片。

### 10.3 页面与组件布局

- 桌面聊天内容最大宽度760px居中，手机单列并留16px侧边距；320px宽度也无页面横向滚动。
- 页头采用紧凑标题「对话记账」和一行说明「发文字或图片，核对后记入账本」。初始示例直接点选填入输入框。功能页面不添加大幅宣传区或装饰图片。
- 聊天页隐藏 LedgerShell 的月份选择条，保留用户身份和账本导航；对话记账日期按消息解释，与概览选中月份分离，避免误记。其他账本页面继续使用月份条。
- 用户文字使用右侧轻色气泡；助手文字左对齐，确认列表在对应助手消息下方全宽展示。图片保留缩略图和点击查看原图入口，预留尺寸避免加载跳动。
- 每笔记录按两行排列：说明在左、金额在右；第二行展示完整日期和分类。金额使用等宽数字，统一人民币符号和两位小数，数字优先于元数据。序号为真实对话指代所需，清晰但弱化视觉。
- 每笔编辑/移除入口持续可见，不依赖悬停；小图标须有可访问名称，点击区域至少44×44px。依赖安装前检查 package.json，新增图标统一用一个允许的图标库。
- 确认列表底部展示「共N笔」及合计金额，唯一主操作为「确认全部记账」，取消使用次要文本按钮。问题摘要先显示原因，再引导定位具体行；颜色与文字共同表达状态。
- 长列表随页面滚动，确认汇总保留在卡片末尾；不在输入栏上方叠加另一条固定操作栏。逐行编辑手机用底部面板，桌面用对话框，提供明确保存/取消与焦点管理。
- 输入栏位于聊天视口底部，文字输入字号至少16px，图片按钮和发送按钮易于单手触达。输入框自动增长到最多4行；处理期间显示状态。视口使用动态高度与安全区，键盘弹出后仍能看到输入框和发送按钮，正文留足底部空间。

### 10.4 状态、动效与验收

空白、上传中、识别中、待补充、可确认、保存中、已保存、失败、已取消及已撤销均需明确样式和实际文案。可确认与保存中容器布局稳定；识别失败保留用户输入并展示重试，不以成功外观掩盖失败。金额修正后短暂强调改动字段，不能用动画延迟确认操作。

使用150至200ms的颜色、透明度或按压反馈；支持减少动态效果偏好。第一版无需引入 Motion 或 GSAP。滚动历史时不强制跳到底部；用户发送消息或正在底部时跟随新内容，有未读新消息时提供跳到底部入口。

视觉验收覆盖320/390/430px手机宽度和桌面、浅色/深色、软键盘、多笔长列表、长说明、图片加载和全部异常状态。提供真实运行截图核对间距、字体、按钮对比度和溢出；检查输入与确认操作的键盘访问、屏幕阅读器标签及状态播报。Lighthouse检查可访问性和性能，结果如实记录；真机验证不能由桌面尺寸模拟替代。
